# セキュリティ

NullClaw はデフォルトで安全な動作（secure-by-default）を採用しています。デフォルトでのローカルバインド、ペアリング認証、サンドボックスによる分離、最小権限がその柱です。

## ページガイド

**このページの対象読者**

- ローカルまたはトンネル経由の NullClaw デプロイを堅牢化する運用担当者
- 設定やランタイムの変更が信頼境界を広げていないかを確認するレビュアー
- ゲートウェイ、ツール、サンドボックス、または公開範囲に関わる処理に手を入れるコントリビューター

## 基本的なコントロール

| 項目 | 状態 | 方法 |
|---|---|---|
| デフォルトではゲートウェイをパブリックに公開しない | 有効 | デフォルトは `127.0.0.1`。トンネルまたは明示的な上書きがない限り、パブリックなバインドを拒否します |
| ペアリングが必須 | 有効 | 6 桁のワンタイムペアリングコードを `POST /pair` で交換します |
| ファイルシステムのスコープ制限 | 有効 | デフォルトで `workspace_only = true` |
| トンネルを考慮した公開 | 有効 | パブリックアクセスは Tailscale/Cloudflare/ngrok/カスタムトンネル経由を想定しています |
| サンドボックスによる分離 | 有効 | Landlock/Firejail/Bubblewrap/Docker を自動選択します |
| シークレットの暗号化 | 有効 | 認証情報は保存時に ChaCha20-Poly1305 で暗号化されます |
| リソース制限 | 有効 | メモリ/CPU/サブプロセスの制限を設定できます |
| 監査ログ | 有効 | 保持ポリシー付きの監査証跡（オプション） |

## プライバシー秘匿化の境界

PII の秘匿化が有効な場合、NullClaw は、プロバイダーの呼び出し、ローカルセッションの永続化、
メモリの自動保存、診断、ベクトル埋め込みの同期の前に、検出した機密値を
`[EMAIL_1]`、`[PHONE_1]`、`[CARD_1]` などの決定的なプレースホルダーに
置き換えます。

再利用可能な秘匿化処理（リダクター）は、デフォルトで一方向に動作します。値は
HMAC-SHA256 フィンガープリントをキーとして管理され、元の平文は保持されません。エージェントは
会話ごとのリダクターに対して、オプトインのメモリ内逆引きマップを使用します。これにより、
同一プリンシパル・単一ユーザー向けの表示経路ではプレースホルダーを元の値に戻せます。共有の
チャンネル、グループ、スレッドのセッションでは、送信される応答内でプレースホルダーがそのまま残ります。
ツールの引数はデフォルトでプレースホルダーを文字どおり保持します。これにより、プロバイダーの
出力がプロバイダーからツールへのデータ流出経路になることを防ぎます。逆引きマップは
プロセスの RAM 内にのみ存在し、サイズに上限があり、会話とともにリセットされ、
メモリ、履歴、JSONL エクスポート、診断には書き込まれません。

リダクターは軽量なテキストスキャナーであり、本格的な DLP/OCR エンジンではありません。対象となるのは、
メールアドレス、電話番号、Luhn チェックを通るカード番号、アンカー付きの
パスポート/ID の値、トークン/シークレットのパターンといった一般的なテキスト形式です。バイナリ画像の内容、OCR テキスト、
EXIF メタデータ、サポートされていないロケール固有の文書形式は、
別のツールが先にテキストとして抽出しない限り、この境界の対象外です。

## 管理されたメモリのワークフロー

メモリを DS 用のアーティファクトにする必要がある場合は、`nullclaw memory export-jsonl` を使用してください。
このコマンドは安定したスキーマの JSONL を出力し、デフォルトでは bootstrap/autosave の
内部エントリを除外します。コンテンツはデフォルトで PII が秘匿化されます。
`--include-pii` は信頼できるローカルの境界内でエクスポートする場合にのみ使用してください。古い
`--redact-pii` フラグは、互換性のために何もしないフラグとして引き続き受け付けられます。

クリーンアップ作業の前には `nullclaw memory hygiene-report` を使用してください。このコマンドは常に
ドライランです。完全一致および正規化後に一致する重複グループを報告するだけで、メモリエントリの削除、
書き換え、再インデックスは行いません。

## オンデマンドの匿名化ツール

`anonymize_text` ツールは、同じ軽量な秘匿化の仕組みを、単発のテキスト断片向けに
エージェントへ公開します。必須の `text` フィールドと、
オプションのブール値 `redact_email`、`redact_phone`、`redact_card`、`redact_id`、
`redact_tokens` を受け付けます。すべてのカテゴリはデフォルトで有効で、明示的に
無効にしたカテゴリはそのまま通過します。

モデル向けの `sqlite_query` ツールは、常に秘匿化された結果を返します。生の
機密な SQLite 出力は、エージェントのツールスキーマを通じて公開されません。また、
`hex(...)` や `substr(...)` などの一般的なテキスト変換/エンコード関数も拒否します。
これらの関数を使うと、クエリ実行後にテキストリダクターが検出できない形に PII が変換されてしまう
可能性があるためです。

呼び出しごとに新しい一方向のリダクターが使われるため、プレースホルダーのカウンターはその呼び出し内で
`[EMAIL_1]` / `[PHONE_1]` から再開され、ツールが返った後に平文の逆引きマップは保持されません。
ユーザーから提供されたテキストを、元の機密値を必要としないチケット、
ノートブック、ログ、エクスポート、下流のツールに渡す前に使用してください。このツールはテキスト専用で、
入力は 256 KiB までに制限されています。バイナリ画像の内容、OCR テキスト、EXIF メタデータは
検査しません。

## チャンネルの許可リスト

- 許可リストベースのチャンネルでは、`allow_from` が空の場合、受信メッセージは拒否されます。
- プライベートなボットにしたい場合は、ユーザー ID/OpenID を明示的に設定してください。
- `allow_from: ["*"]`: すべての送信元を許可します（高リスク）。
- それ以外の場合: 完全一致の許可リスト、またはチャンネル固有のフォールバック/グループポリシーの動作になります。

## ペアリングと Webhook 認証の境界

- `/pair` は POST のみを受け付け、`X-Pairing-Code` を必要とします。
- 無効なペアリングの試行が繰り返されると、レート制限と一時的なロックアウトが発動することがあります。
- A2A が有効な場合、`/.well-known/agent.json` と `/.well-known/agent-card.json` は公開のディスカバリードキュメントになります。
- `gateway.require_pairing = true` のままにしておくと、`/webhook`、`/a2a`、`/media/transcribe` は Bearer 認証で保護されます。ペアリングを無効にすると、ローカルバインドではその Bearer チェックがなくなります。
- Telegram の Webhook 配信では、`X-Telegram-Bot-Api-Secret-Token` が `channels.telegram.accounts.<id>.webhook_secret` と一致する必要があります。
- チャンネル固有の受信 Webhook はそれぞれ独自の認証または署名のルールを持つため、すべてがゲートウェイの Bearer 認証を使うかのように記述すべきではありません。

## Nostr 固有のルール

- `dm_allowed_pubkeys` がより厳しい場合でも、`owner_pubkey` は常に許可されます。
- 秘密鍵は暗号化された状態（`enc2:`）で保存され、チャンネルの実行中にのみメモリ上で復号されます。

## 推奨されるセキュリティ設定

```json
{
  "gateway": {
    "host": "127.0.0.1",
    "port": 3000,
    "require_pairing": true,
    "allow_public_bind": false
  },
  "autonomy": {
    "level": "supervised",
    "workspace_only": true,
    "max_actions_per_hour": 20
  },
  "security": {
    "sandbox": { "backend": "auto" },
    "audit": { "enabled": true, "retention_days": 90 }
  }
}
```

## シェルの環境変数

デフォルトでは、安全な最小限の環境変数（`PATH`、`HOME`、`TERM`、`LANG`、`LC_ALL`、`LC_CTYPE`、`USER`、`SHELL`、`TMPDIR`）のみがシェルの子プロセスに渡されます。これにより、API キーや認証情報の漏えい（CWE-200）を防ぎます。

### パスを検証する環境変数

デプロイによっては、ボリュームマウントを通じてツールを注入する場合があります（例: Kubernetes のツールボックス用 init コンテナ）。こうしたツールは共有ライブラリを見つけるために `LD_LIBRARY_PATH` などの環境変数を必要とすることがありますが、`LD_LIBRARY_PATH` を無条件に渡すことはセキュリティリスク（ライブラリインジェクション）になります。

`tools.path_env_vars` 設定では、**値がプラットフォームのパスリスト**（Unix では `:`、Windows では `;` 区切り）である環境変数を指定できます。変数を子プロセスに渡す前に、各パス要素がサンドボックスに照らして検証されます:

1. すべての要素は絶対パスでなければなりません
2. すべての要素は `realpath` で解決されます（正規化され、シンボリックリンクがたどられます）
3. すべての要素はワークスペースまたは `allowed_paths` の内側になければなりません
4. システムのブロックリスト（`/etc`、`/usr/lib`、`/bin` など）は常に拒否されます

**いずれか**の要素が検証に失敗した場合、その変数全体が除外されます。

```json
{
  "autonomy": {
    "allowed_paths": ["/opt/tools"]
  },
  "tools": {
    "path_env_vars": ["LD_LIBRARY_PATH", "PYTHONHOME", "NODE_PATH"]
  }
}
```

上記の設定で、コンテナ環境に `LD_LIBRARY_PATH=/opt/tools/usr/lib:/opt/tools/lib` が設定されている場合、シェルツールは両方のパス要素を（`allowed_paths` を通じて）`/opt/tools` に照らして検証し、変数を渡します。`/tmp/evil:/opt/tools/lib` のような攻撃者が制御する値は、`/tmp/evil` がワークスペースや許可されたパスの内側にないため拒否されます。

## 高リスクな設定

以下の設定は信頼境界を大幅に広げるため、管理された環境でのみ使用してください:

- `autonomy.level = "full"`
- `autonomy.level = "yolo"`
- `allowed_commands = ["*"]`
- `allowed_paths = ["*"]`
- `block_high_risk_commands = false` — 破壊的なコマンド（`rm`、`sudo`、`dd`、`mkfs` など）を有効にします
- `block_medium_risk_commands = false` — ネットワーク/転送コマンド（`curl`、`wget`、`nc`、`scp` など）や、`git commit`、`npm install`、`touch` などのローカルな変更を含む中リスクのコマンドを有効にします
- `gateway.allow_public_bind = true`

## ワークスペースのシークレット監査

`nullclaw workspace audit` は、ワークスペース、ステージされた Git の差分、または Git のリビジョン範囲をスキャンし、シークレット漏えいの可能性を検出します。検出処理はすべてローカルマシン上で実行され、CI との連携に適した安定した JSON 形式で検出結果を出力します。

### 検出対象

| 検出器 | 検出元 |
|---|---|
| 既知のトークンプレフィックスのフィンガープリント | `AKIA…`、`ghp_`、`gho_`、`ghs_`、`glpat-`、`xoxb-`、`xoxp-`、`sk-`、`sk-proj-` など |
| スコアベースの代入マッチャー | `KEY=value` / `key: value` を名前付きの要素に分解し、シークレット関連キーワードの辞書と照らしてスコアを付けます |
| 形式ベースの検出器 | `-----BEGIN PRIVATE KEY-----` の PEM ブロック、URL に埋め込まれた認証情報（`scheme://user:pass@host/...`） |
| 高エントロピーの走査 | 16 文字以上でシャノンエントロピーが 4.0 以上のトークン状の文字列のうち、UUID、git のコミットハッシュ、プレースホルダー文字列ではないもの |

終了コードは `--fail-on <none\|medium\|high\|critical>`（デフォルトは `high`）に従います。CI パイプラインでは `--json` と組み合わせて使用してください。

### オプションの LLM トリアージ

`--llm-triage` フラグは、エージェントに設定された LLM プロバイダーを使って検出結果を分類する、オプトインの第 2 段階を追加します。分類器には、生のシークレット値を含まない**プライバシーを保護したエンベロープ**が渡されます:

| エンベロープに含まれるもの | エンベロープに含まれないもの |
|---|---|
| `variable_name`、`file_path`、`extension`、`detector` | シークレット値そのもの |
| `token_type_fingerprint`（決定的なローカル検索） | シークレットの部分文字列 |
| `length`、`charset`、`entropy` | シークレット周辺の行の内容 |
| マスクされた行のコンテキスト（例: `KEY=<SECRET:len=40,charset=base64url,entropy=5.3>`） | 正規の語彙に含まれない周辺の単語 |
| 約 60 個の正規のセキュリティ/サービス用語のホワイトリストでフィルタリングされた `nearby_keywords` | 顧客名、内部ホスト名、業務上の識別子 |
| 決定的なフラグ: `is_test_path`、`is_example_file`、`is_in_comment`、`is_in_docstring` | それらのフラグに対する LLM の推論 |

エンベロープのスキーマにはバージョンがあり（`schema_version: "1"`）、各エンベロープには追跡用の SHA-256 の `envelope_hash` が付与されます。

3 つのモードがあります:

- `--llm-triage off`（デフォルト）— LLM の処理は行われず、動作は通常のスキャンと同じです。
- `--llm-triage dry-run` — 送信される*はずの*エンベロープを（stderr に）出力し、ネットワーク呼び出しは一切行いません。機能を有効にする前に、何がマシンの外に出るかを確認するために使用してください。
- `--llm-triage external` — 設定されたプロバイダーの vtable を通じてエンベロープを送信します。`--llm-provider` / `--llm-model` で上書きされない限り、`workspace_audit.llm_triage.{provider,model}` があればそれを使用し、なければ設定済みのプライマリプロバイダー/モデルを使用します。プロバイダーがローカル（例: Ollama）の場合、エンベロープはマシンの外に一切出ません。

通常のエージェントのモデルを変更せずに、監査のトリアージをより小さなモデルやローカルモデルに固定するには、次のように設定します:

```json
{
  "workspace_audit": {
    "llm_triage": {
      "provider": "ollama",
      "model": "qwen2.5-coder:7b",
      "max_calls": 20
    }
  }
}
```

この設定だけでは外部の LLM 呼び出しは有効になりません。運用担当者が `--llm-triage external` を指定する必要があります。CLI フラグの `--llm-provider`、`--llm-model`、`--llm-max-calls` は、1 回の実行に限ってこれらの設定値を上書きします。不明なプロバイダー名は、そのプロバイダーに明示的な `models.providers.<name>.base_url` がない限り拒否されます。そのため、タイプミスによって監査のエンベロープが気づかないうちにフォールバックのプロバイダーへ送られることはありません。

`external` のリクエストはすべて `<config-dir>/audit-log.jsonl` に追記されます。NullClaw は LLM の呼び出し前にエンベロープを含む `sent` イベントを書き込み、応答後に `envelope_hash` をキーとする `verdict` イベントを書き込みます。このログは追記専用で、どのメタデータが送信されたかを事後に検証するためのものです。

### 運用上の注意

- デフォルトの `--llm-triage off` では、既存のスキャンの動作は変わりません。誤検知のトリアージが問題になっている場合に、明示的に有効にしてください。
- プライバシーが重要なデプロイでは、`--llm-triage external` を有効にする前に、`workspace_audit.llm_triage.provider` を `ollama`（または別のローカル専用プロバイダー）に固定してください。
- 判定値は参考情報です。`false_positive` と判定された検出結果は除外され、`real_secret` と判定された場合は重大度が調整されることがあります。候補をそもそも表示するかどうかについては、決定的な第 1 段階の検出器が引き続き最終的な判断を下します。
